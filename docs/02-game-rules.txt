灯火大排档 玩法与状态逻辑

核心循环
有限食材，点击当前可选牌进入7格共享备菜。某桌配方凑齐后自动扣除对应食材、释放备菜格，交给炒锅排队。炒完立即出锅送菜；送达才增加收入，旧单立即退场，随后补新单。收入达到目标即通关，不要求清空食材台。

配方
data/recipes.json包含10道双食材、10道三食材，每种食材各需1份。油、盐、酱汁等默认调味不占备菜槽，也不算可选食材。成品图避免额外撒未列出的葱花或蔬菜。
三食材菜结算为基础价×1.5，双食材按基础价结算。价格为制作初值，正式关卡需要实机调平衡。d11是原三料“香菇鸡丁”的资源映射；d03是双料版本，两者不要混用。
生成同屏新订单时，避免一份配方是另一份配方的子集。例如d03的香菇＋鸡肉不能和d11的香菇＋鸡肉＋葱同时作为未备齐订单，否则双料会先被自动消费。

状态
collecting：仍收食材。
queued：已扣料，不再重复接收；等待锅空。
cooking：进锅、颠锅和倒菜。
delivering：锅已释放，成品独立飞向订单。
exiting：成品已送达且结算，旧单立即退出。
collecting：新单显示，可继续收料。
completed：本关已通关，最后的结算反馈完成。

并发规则
炒锅队列和上菜动画分开。上一道出锅时就释放锅，下一道可以立刻入锅，不用等上一道飞到菜单。
每桌按自己的送达和退场时间刷新，不等待其他桌，也不等待整段动画结束。
禁止等动画Promise结束才扣料、禁止按帧重复加钱、禁止已配齐订单继续吃食材。
game-core.js以确定的时间事件推进逻辑，渲染层只读取snapshot和drainEvents。不要把DOM动画回调当成唯一业务时钟。

输入与容量
点击时立即移除被选牌并保留一份飞行中的入槽预约；到槽后才加入buffer并检查配方。
buffer＋incoming最多7份。第8次输入应拒绝并给轻反馈，不能先越界再补救。
当配方完整时同一帧移走配方食材；匹配只检查collecting订单，按订单先后选择可完整制作的菜。
不要在最后一颗食材仍在飞行时判“备菜满”失败，先完成入槽和配方消费。

失败与道具参考
game-core提供可执行初值：无任何进行中任务，备菜已满且没有可完成配方时失败；食材全部用完、任务全部结束且收入未达标时失败。正式项目如采用不同规则，应明确更改，不把动画等待当成失败原因。
撤回只撤销尚未被配方消费、已到槽的一份食材；已排队订单不能用撤回重复取回。
暂存移动一份备菜到最多2份的暂存区，取回时再匹配配方。只有成功移动才扣次数。
提示只标记一张当前可选、某个未备齐订单需要的食材，不能指向被覆盖暗牌。示例次数为撤回1、暂存2、提示1，可调。

通关计时
首次达到目标时冻结playTime；停止接收新输入，结算反馈完成后显示成功弹窗。浏览弹窗、暂停和后台停留不继续计入成绩。
达到目标以后不重复结算或继续加分。剩余食材不构成通关条件，也不在成功弹窗单列。

验证
在包根目录运行 node src/verify.cjs。包含配方数量、一次扣料、排队与送菜并发、独立换单、容量保护、暂停、冻结计时、层间遮挡、撤回暂存、配方子集冲突、动效与资源校验。
