# 关卡配置、生成与难度验证

适用版本：`generatorVersion: 5`，2026-11-21。当前实现采用统一菜品列表、最多三道当前订单和经典三道具。机器人分数不等于真人胜率；无道具见证只证明有解，不能据此认定普通玩家容易通关。

## 2. 直接调整某关的菜谱

唯一生产入口是 `shared/data/level-config.js`，三端读取同一份配置。`shared/data/recipes.json` 定义配方和单价；关卡配置不重复填写材料总数或收入。

```js
{
  level: 1,
  difficulty: 'easy',
  shape: 'islands',
  layers: 2,
  seed: 15838, // 实际精选值以文件为准
  orders: ['d01', 'd02', 'd14', 'd01', 'd02'] // 顺序补入当前三道；每个 ID 是一份菜
}
```

- orders 是一个完整列表，禁止嵌套分桌数组。每个 ID 代表一份菜，重复 ID 表示同一道菜的多份订单。开局取前三份；任意一道配齐，就按全局游标预留下一份，0.42秒交接后显示并可收料。
- 改某关只需改该行 `orders`。材料总账、成菜份数、单价合计和预期收入自动推导。三张卡是并发显示容量，不是三条补单队列；待补列表未空时维持三张，耗尽后才依次减为二、一、零。
- `levels` 从 1 开始连续编号，不能重复或留空；新增手工关追加在末尾。`repeat` 控制手工关之后的循环计划，`seeds` 控制扩展关的精选种子。
- `shape` 支持 `pairs / islands / ring / bridge / lantern / twins`；`layers` 必须能容纳实际材料，且不超过全局上限。不为多牌缩小现有牌尺寸。
- `difficulty` 选择下面的构造参数。它不是实测难度分数，必须重新分析。
- `seed` 为 0–4294967295 的整数；同版本、配置、布局和种子确定性复现。更新配置后内容指纹 `contentId` 改变，首通去重仍只依据主线关号。
- 可在某条配置中增加 `greedyTarget: [下限, 上限]`，覆盖候选筛选的无道具贪心目标；`lookaheadTarget` 控制可见信息前瞻成绩，`toolTarget` 控制三种道具各一次的成绩。`toolGainTarget`控制最低工具提升，未配置时沿用0.15。当前留存版逐关校准贪心区间，前瞻与工具区间为[0,1]、最低提升为0，只报告观察值，不以视频收益或低通过率作为筛关目标；它们都不是真人胜率。
- `levels:generate --apply` 会重新格式化这份数据并写回种子，保留队列和支持的配置字段；先检查候选报告，再应用。

## 3. 构造参数、几何与约束

| 档位 | 构造备菜峰值预算 | mixing |
| --- | ---: | ---: |
| easy 入门 | 3 | 0 |
| normal 家常 | 4 | 1 |
| hard 忙碌 | 5 | 2 |
| expert 挑战 | 5 | 3 |

`prepLimit` 只约束构造见证，玩家始终七格；见证峰值不是最优路线的最低容量。mixing=0 偏向即时成菜，其他值偏向交错与持料，不是难度倍率。

`shared/data/board-templates.js` 定义六种轮廓。0 格始终留空，牌位按轮廓从中心向外生长；按总牌数从下到上分配准确数量，上层位置由下层支撑。相邻层交替使用 `(32,-24)` 偏移，最终整体居中于 `(55,536,818,791)` 的食材区。保持原牌大小与触摸尺寸，层数增加不压缩字体或食材。

`board-geometry.js` 统一矩形相交、遮挡图和绘制顺序。所有更高且相交的牌都算遮挡者；全部移走后才可选。绘制和引擎按同一层级顺序排列，输入反向命中；任意层解锁都能反馈，不再只处理 layer=0。

配置与生成必须满足：

- 每种配方各材料一份，完整材料与所有订单逐项相等。
- 不同配方不得互为子集；同一道菜允许重复。三张订单共享材料时按列表序号优先匹配，并逐份扣料，不会一份材料完成两道菜。统一队列允许重复菜并发，原“三桌不能共用材料”约束不再适用；全关与开局材料集中度限制继续生效。
- N≥20 时，全关单料最多 `ceil(N×0.20)` 张。
- 开局单料最多 `ceil(可取牌数×0.30)` 张；小盘面取整后实际比例可能高于 30%，报告同时给数量和分母。此约束不套用到残局。
- 同层不能重叠，全部牌在实际绘制区内，形状有足够牌位。
- 摆牌在 24 个合法拓扑分配候选中降低开局集中与同料相邻；不允许在生成见证后任意洗牌。

## 4. 生成与可解保证

```text
配置完整菜品列表 → 菜品/材料总账 → 对应数量的形状牌位
→ 受备菜预算限制的材料序列 → 合法拓扑顺序赋值
→ 开局集中与相邻材料筛选 → 真实 Engine 回放至最后送达
```

材料序列搜索维护库存、备菜与全局游标及当前三个订单索引，缓存失败状态，最多 20,000 个节点。几何不决定材料预算。每个返回的牌堆还需通过 .01/.05/.1 秒连续点击回放；若因菜单交接与材料竞争偏离，则确定性换序重试，最多二十四次，`generationAttempts` 记录次数。全部失败时抛出错误，不返回未验证牌堆。

稳定模型每次等待材料和菜单交接完成；真实回放另外覆盖连续输入、容量预约、烹饪与送达。生产生成只运行有界构造，完整候选搜索及分析留在开发工具中。

### 4.1 难度与“有无解”是两种检查

生产生成采用先构造解、再验证解的方式：`prepLimit/mixing` 影响构造路线的持料与交错，合法拓扑取牌顺序保证几何可达，真实引擎回放验证容量、订单交接、全部材料和最后送达。因此当前主线每副牌都存在无道具解；改种子或把机器人胜率压至零，不能把它变成数学意义的无解关。

难度采用多策略抽样：随机、当前订单贪心、几何解锁、可见信息前瞻分别执行不同决策种子，统计无道具和不同工具预算的通过率。份数、层数、可取牌数、集中度、持料峰值都是辅助指标，不能单独定难度。见证峰值只是已知路线的占槽上界；求最小容量需要下界证明或逐容量搜索。

开发求解采用深度搜索、状态缓存与预算限制，状态包含已取牌集合、备菜顺序、移出区、当前订单、全局游标及工具使用情况。有解返回一条真实引擎可复验的操作路线；完整搜尽才可在该模型中报无解；节点预算耗尽则为未知。三种状态不能混用，这与约束求解中的 [FEASIBLE / INFEASIBLE / UNKNOWN 区分](https://developers.google.com/optimization/cp/cp_solver/)一致。本项目未引入 OR-Tools，仍使用现有 JavaScript 求解器。稳定状态搜索没有穷举全部连续时间输入或所有洗牌排列，其无解结论必须注明模型边界。

### 4.2 可配置道具生成与验证关 TG01

实验生成模式 `tool-gate` 的配置在 `configs/experiments/tool-gate.json` 与 `tool-gate-triple.json`，支持菜单、种子、形状、层数、首道菜容量门槛及候选／搜索预算。`npm run levels:generate:tool-gate -- --config configs/experiments/tool-gate.json --count 3` 批量生成，材料位置自动分配；每个结果都须有无道具无解证书和一次移出的真实通关见证。模式只在实验室和离线命令中使用，不进入主线或 native 包；生产生成器继续拒绝 `requires-tool`。配置字段、输出结构、导入试玩、失败诊断和边界见[实验道具关生成说明](16-tool-gate-generation.md)。

固定 TG01 及通用证明器保留在 `platforms/web/lab/experiments/tool-gate.js`，用来独立复核下述容量屏障原理。固定验证关不等于生成模板中的手填材料矩阵；生成模式不要求逐层配置材料。

TG01 有七份菜、五种配方、十四张食材、七层双岛。前面三道是番茄炒蛋、青椒肉片、香菇鸡丁；后续四道由西兰花虾仁、芹菜牛肉组成。每座岛顶部四张都是后续订单材料，底部三张才是当前三道菜的材料，左右岛各提供每道菜的一种材料。没有缺料、删料或临时改菜单。

证明器依据真实遮挡图，枚举每道初始配方的材料牌组合，计算“选中这些材料及其全部递归遮挡者”的并集张数，取最小值：

| 第一道可能完成的菜 | 至少要取的牌数（含成菜材料） |
| --- | ---: |
| 番茄炒蛋 | 10 |
| 青椒肉片 | 12 |
| 香菇鸡丁 | 14 |

首道菜之前没有任何消耗，也没有后续补单，所以这批牌必然全部占用库存。最小值 10 大于主槽容量 7，即可证明不使用道具必无解；该结论也覆盖飞行预约、任意连点与等待时长。只有几何下界大于容量时才给无解证书；下界小于等于容量仍为未知，不能据此保证有解。只用撤回也不增加可同时保存的材料数；洗牌会改变食材与遮挡关系，须重新分析，未声称只用洗牌一定失败。

一次移出提供额外三格，合计可保存十张。在主槽六张时移出最前三张，继续取到番茄和鸡蛋，第一道完成后订单释放并开始消耗上层材料，最后逐张取回移出区材料并完成全部菜。真实引擎路线使用一次模拟完整视频奖励、只执行移出，没有撤回、洗牌或求解提示效果；总收入 260。该路线证明“至少一道具有必要，且一次正确使用移出足够”，不代表任意使用时机或任意一种道具都保证通关。

验证结果：

- 真实引擎逐分支穷举 255 个稳定状态、128 条失败终局，0 条胜利，均在取出七张且未成菜时失败；独立紧凑搜索也判无道具无解。
- 容量下界 10，加上容量 10 的无道具真实回放，得到该关最小无道具容量恰为 10。
- 一次移出路线在稳定输入、0.01/0.05/0.1 秒连续输入下均通关；主槽峰值七张、主槽加移出峰值十张，七道菜全部送达，移出区清空。
- 失败后主槽 7 → 模拟完整视频移出 → 主槽 4、移出区 3 → 继续求解与回放通关；取消、真实 SDK 和旧局隔离仍由原广告测试覆盖。

运行 `npm run analyze:tool-gate` 生成 `reports/levels/tool-gate-TG01.json`，包含配置、几何证书、各搜索状态和真实操作路线。`tests/verify-tool-gate.cjs` 已加入常规及完整回归。浏览器入口为 `http://127.0.0.1:4173/platforms/web/lab/?experiment=tool-gate`：先点“验证无道具并回放失败”，可用“模拟视频：移出一次”续玩，也可点“回放一次移出通关（模拟）”。它不播放广告、不发经营奖励；普通关与实验关的预算、重开和导出记录各自保持一致。

当前独立生成目标已实现首道菜之前的一次移出门槛；中段门槛、多种工具和多次视频暂未实现。若后续扩展中段门槛，必须对所有无道具分支证明必经，不能只检查一条失败路线。数量更大的关卡优先采用可验证的局部容量屏障，不依赖全盘暴力穷举。道具生成仍不接入主线；两端真实广告单元也尚未配置。

## 5. 经典三道具与激励视频

参考《羊了个羊》公开的经典玩法：[2022 年道具说明](https://www.doyo.cn/news/206430.html)、[使用方法](https://jingyan.baidu.com/article/4e5b3e1902f0c2d0901e24d9.html)。不同模式和时期的额外复活、分享获取次数存在差异；本项目复用三种基础效果和每局各一次的上限，获取方式采用激励视频。

| 显示名称 | 内部键 | 实际效果 |
| --- | --- | --- |
| 移出 | stash | 主槽至少三张时，最前面三张按原顺序移到槽外；保留材料，可逐张点击取回。不是删除、自动做菜或增加主槽上限。 |
| 撤回 | undo | 最近一张未消费的备菜回到原牌位，释放一个槽；已经进入菜品的材料不可撤回。 |
| 洗牌 | shuffle | 对所有尚未取走的牌随机重排食材图案；数量、位置、层级、遮挡、备菜、移出区、订单和厨房不变。 |

三种道具每局各一次，总计最多三次广告；重开重新计数。主线无免费工具额度，只有完整视频回调后才立即执行所选效果。已使用的同一道具不能重复领取。失败满槽时可撤回或移出；洗牌不释放备菜格，因此不能用洗牌复活满槽。食材仍在飞行时等待入槽，防止作用对象不明确。未知广告、取消、错误、重复回调、旧局和已释放会话均不发奖。

不再提供玩家提示道具，也不在广告后附送完整信息求解步骤。道具是局面操作，不承诺使用后自动通关；洗牌使用确定性伪随机数以便复现，保持剩余材料多重集合，不偷偷补料、换菜单或改容量。失败入口按实际合法效果提供，不用求解器筛掉难以证明的局面。

三格移出区独立于七格主槽，取回仍检查飞行预约容量。即使牌堆清空，移出区未空也不能通关或判库存耗尽。`App` 注入 `rewardedRescue`；无真实广告单元或尚未加载时，失败救援入口不展示，道具点击说明视频暂不可用。两端 `src/ad-config.js` 配置广告单元，SDK 的 show/load 成功都不是奖励，只有 `onClose({isEnded:true})` 发奖，广告期间不计时。

`level-search.js` 仅用于开发求解，维护备菜顺序、来源、三格移出区、菜单游标和一次性工具状态。返回 solved/unsolvable/unknown；找到的路线必须真实引擎复验。洗牌排列空间未穷举：允许尚未使用的洗牌时，搜索未找到路线只能记 unknown，不能证明无解。最低容量与安全选择仍给上下界。

## 6. 自动工具与复现

已有命令均从仓库根目录运行：

```sh
npm run build
npm test
npm run test:levels
npm run test:levels:full
npm run test:levels:ui
npm run test:difficulty
npm run analyze:tool-gate
npm run levels:generate:tool-gate -- --config configs/experiments/tool-gate.json --count 3
npm run test:tool-gate
npm run analyze:levels -- --levels 1:100 --trials 32 --cases
npm run analyze:levels -- --levels 1:20,64 --trials 64 --policy-seed-offset 131071 --policies greedy,lookahead --tools
npm run analyze:levels -- --levels 1,20,40,64 --trials 16 --policies greedy,lookahead --tools --solve
npm run levels:generate -- --levels 1:100 --candidates 100 --trials 64 --seed 20261118
npm run levels:generate -- --levels 1:100 --candidates 100 --trials 64 --apply
npm run levels:replay -- --level 20 --policy greedy --policy-seed 997 --budget free
npm run levels:replay -- --case reports/levels/replay.json
npm run serve
```

- `test:difficulty` 对前一百关固定样本逐关检查配置目标，失败退出；`--policy-seed-offset` 使用不同于筛关训练的随机决策种子复核，避免只拟合训练路径。
- 分析支持 `--levels 1:20` 和 `--levels 1,20,40:45`。旧位置参数 `200 32` 现在表示实际第 1–200 关、每副每策略 32 次，不再强制覆盖四档同一个 40 张牌结构。
- 分析输出 JSON 与 CSV，逐关给菜谱、张数、层数、开局材料、策略分数与未知救援数；`--cases` 保存代表失败路径。`--solve` 增加 oracle、最低容量上下界和根状态安全选择范围；大型关卡宜按需单独运行。
- `--tools` 比较 none（零道具）、free（三种道具各一次）、ad1、ad2、ad3（最多一/二/三次视频，无免费额度）；随机策略始终单独测零道具。实际工具行为和暂存取回均通过引擎执行。
- 策略为 random、greedy、unlock、lookahead。greedy 只看当前订单和可取牌；unlock 还使用遮挡几何，不是普通玩家胜率预测；lookahead 只前瞻当前已知订单和可取材料，不读取隐藏食材和后续菜单。oracle 明确读取完整信息。
- 候选同时检查零道具贪心、可见信息前瞻、道具策略与提升幅度，再按指定 trials 复核。超出目标时默认拒绝写回；`--allow-outside` 仅供显式开发试验，不应当作正常验收。
- 失败记录含生成器版本、配置、种子、配方/布局 SHA-256、策略版本、策略种子、道具预算、动作与结果。CLI 校验版本与哈希，不兼容时要求对应源码。可重放稳定操作，也可重放实验室导出的 tick/pause 时间轴。
- `reports/levels/` 为忽略的开发产物，测试脚本和候选库不进入 native 包；打包时复用相同订单队列，解码后的配置与 Web 一致。

浏览器实验室：`http://127.0.0.1:4173/platforms/web/lab/`。支持逐关配置 JSON 预览、真实取牌、任意层剖面、当前状态求解、单步和整条见证、三种基础策略、记录导入导出。它不读写经营存档，剖面不改变真实可选关系，离线局时不作为真人局长。复杂工具预算与批量比较走 CLI。

## 8. 调整与发布流程

1. 修改单关 orders、形状、层数或构造档位；先检查材料总账及配方兼容。
2. 固定样本分析，检查逐关分布和异常种子；对候选结果做独立策略种子复核，避免只调到机器人样本。
3. 生成候选，检查 JSON，再显式 `--apply` 写回种子；实验室复核教学、关键节点及残局；开发求解与见证使用完整信息，不能用于判断普通玩家难度。
4. 执行完整 build、npm test；算法改动追加 `test:levels:full`。真实手机检查触摸、识别、帧率、后台、字体与广告。
5. 重算首通收入、收藏和装扮节奏；首通关号去重及历史钱包不变。更新本文和经营文档。

算法改变导致相同输入发牌变化时递增 generatorVersion；只改具体队列或种子由内容指纹区分。当前无账户/云存档、真人校准与正式广告单元验收，不把本地模拟通过写成发布验收完成。
