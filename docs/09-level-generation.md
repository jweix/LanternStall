# 关卡难度设计与实现

适用版本：`generatorVersion: 2`。本文件是难度设计、发牌实现、验证和调参的统一说明，描述当前有效方案。算法或参数改变时直接修订相关章节和结果，移除失效内容，不追加开发流水账。

按需阅读：设计难度看第 1、3 节；修改实现看第 2 节；验证看第 4 节；调参看第 5 节；定位代码与复盘看第 6 节。

## 1. 设计目标与难度来源

每关先决定做哪些菜、各做多少份，再展开材料，最后安排材料的取出顺序和堆叠位置。当前固定 **40 张牌、25 张上层、15 张下层、7 格备菜**，通过以下因素形成难度差异：

- **遮挡依赖**：急需的材料被几张牌压住，取到它之前需要先收多少其他材料。
- **材料交错**：连续完成一道菜，还是同时持有几道未完成菜的材料。
- **菜谱与补单**：材料属于当前订单，还是要等后面的订单才能用；种类越多，判断和腾槽越复杂。
- **配方长度与共享材料**：三料菜占用更多空间；不同配方共用材料时，选择会互相影响。配方子集冲突必须避免。

总材料能配平不代表任意堆叠都有解。目标是生成**存在无道具解、可按种子复盘、固定策略下有难度梯度**的关卡；不要求任意点击都能赢，不按手速评难度。

研究参考是《羊了个羊》的公开求解器和复刻环境，未取得官方生成源码。本项目独立实现遮挡依赖与受控生成，不声称复原官方算法。来源见第 7 节。

## 2. 生成原理与可解性

```text
关卡号 + 档位 + 32 位种子
  → 菜谱池与每道菜份数
  → 三桌有限补单队列
  → 配方展开为 40 份材料
  → 错层位置与遮挡依赖图
  → 搜索符合备菜预算的材料序列
  → 沿合法移除顺序把材料写入牌位
  → 真实引擎回放至最后上菜，成功才返回关卡
```

### 菜品计划与材料总账

`createDishPlan` 轮换主菜，从兼容菜谱中挑选菜谱池；入门倾向较少材料种类，其他档位倾向较多种类。每道菜至少一份，按配方长度分配份数，满足：

`2 × 双料份数 + 3 × 三料份数 = 40`

每道菜固定归属一桌，按工作量分配桌位，再用种子打乱各桌补单顺序。`dishPlan` 保存菜品、桌位和份数，`orderPlan` 保存完整补单队列，`ingredientCounts` 保存材料总账。

`Engine` 严格按各桌队列补单，上齐后停止；各桌在配齐后的0.42秒独立补单，不等待旧菜送达；出菜快慢不改变材料预算。有效库存为未取牌＋备菜＋在途＋暂存，已扣料厨房任务不计入补单库存。合法有限计划的剩余材料总账足以覆盖每份后续订单，耗尽后不额外刷单。生成器要求整个菜谱池互不构成配方子集；引擎另外检查任意跨桌未来订单都兼容，避免异步补单产生冲突。

### 几何遮挡与材料赋值

`createGeometry` 保留上层 5×5，按难度从 25 个候选位置选出 15 个下层位置，下层偏移为 `(+32, -24)`。位置评分按被遮挡数量和随机扰动计算，低难度倾向边缘，高难度倾向内部。

对于每张牌，把所有层数更高且与它相交的牌记为父节点；相交判断复用 `Core.overlap`。只有父节点全部移除后，该牌才能取走。这形成有向无环的遮挡依赖图。

`placeFoods` 每一步随机选择一张当前可取的牌位，下层解锁后优先选择下层；按材料序列逐张填入。因此，材料序列对应一条符合几何遮挡的移除路线 `solution`。材料写入后不再进行任意洗牌。

### 备菜调度与回溯

`createFoodSequence` 维护剩余库存、备菜数量和三桌订单游标。入门优先成菜，其他档位偏向保留交错材料，但每一步都检查备菜预算，并预留至少完成一道当前订单的空间。

补单可能让剩余材料暂时无用，因此局部容量检查之外还要回溯；相同订单游标与备菜库存的失败状态会被缓存。搜索最多访问 20,000 个节点，无法构造则报错，不返回未经验证的牌堆。

构造模型把上一单交接（0.42秒）视为已完成，再安排下一次选择；最终由 `verifySolution` 使用真实 `Engine` 逐张点击，检查遮挡、飞行预约和容量，并等最后上菜后确认 `won`。生成回放当前每次先推进 `.3` 秒，有进行中任务时再推进 `10` 秒。玩家输入仍然不锁定，烹饪与送菜继续并行。`tests/verify-handoff.cjs`另外以0.01秒间隔尝试点击四档完整见证，满容量才等格位释放，检查异步换单下40份材料与收入仍准确。

**保证的范围**：返回的牌堆有一条经过真实引擎验证的无道具通关路线。见证路线的备菜峰值不是最优路线所需的最低容量；玩家偏离路线后也可能失败。

## 3. 当前四档参数

参数定义在 `shared/core/levels.js` 的 `PROFILES`：

| 档位 | `recipeCount` | `tripleRecipes` | `tripleDishes` | `prepLimit` | `bury` | `mixing` |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 入门 easy | 3 | 1 | 4 | 3 | 0 | 0 |
| 家常 normal | 4 | 2 | 8 | 4 | 0.35 | 1 |
| 忙碌 hard | 5 | 3 | 10 | 6 | 0.75 | 2 |
| 挑战 expert | 6 | 5 | 12 | 7 | 1 | 3 |

| 参数 | 含义与调节作用 |
| --- | --- |
| `recipeCount` | 本关不同菜谱总数；增加后通常有更多材料种类和未来订单材料。 |
| `tripleRecipes` | 菜谱池中三料菜的种类数；其余为双料菜。 |
| `tripleDishes` | 本关三料菜总份数；双料份数由 `(40 - 3 × tripleDishes) / 2` 推导。 |
| `prepLimit` | 构造路线允许的备菜峰值预算；调高允许更多交错，玩家容量始终为 7。 |
| `bury` | 下层位置倾向，建议范围 0–1；评分为 `遮挡者数量 × (2 × bury - 1) + [0, 0.9) 随机数`。低于 0.5 倾向边缘，高于 0.5 倾向内部。 |
| `mixing` | 0 时偏向低种类菜谱和即时成菜；大于 0 时偏向多种类菜谱，并提高调度中对即时成菜的惩罚。它不是线性的难度倍率。 |

四档的“双料/三料份数”依次为 `14/4、8/8、5/10、2/12`，材料均为 40 份。`profileFor` 让前四关依次体验四档，随后循环“家常 → 忙碌 → 家常 → 忙碌 → 挑战”。

难度由多参数共同决定，不能把某个参数当成难度分数。当前忙碌和挑战的遮挡边数相同，差异主要来自菜谱、补单和材料交错。

## 4. 验证方法与当前基线

先验证可解性与规则正确，再比较策略表现，最后做真人校准。

| 检查 | 覆盖与通过条件 |
| --- | --- |
| 每次生成的 `verifySolution` | 真实点击、容量预约、配方消费、烹饪和送达，最终必须为 `won`。 |
| `tests/verify-game.cjs` | 默认 100 关通关，以及快速输入、暂停、换关、暂存、失败和最后上菜等生命周期规则。 |
| `tests/verify-levels.cjs` | 四档各 100 个种子，核对 40 张牌、材料与份数、完整无道具通关、实际收入、确定性及 20 道菜覆盖；192 条策略路径与真实引擎结果一致；固定样本难度回归。 |
| `tests/verify-core.cjs`、`tests/verify-handoff.cjs`、`tests/verify-wechat.cjs` | 核心规则、资源和微信包启动、生命周期、坐标变换等集成检查。 |
| `scripts/analyze-levels.cjs` | 输出各档材料种类、遮挡边数、见证占用、策略通关率和生成耗时，供调参比较。 |

策略样本固定为每档关卡号 `1–50`，使用默认关卡种子；每张牌堆每种策略跑 16 次，策略种子为 `trial × 997`，即每档每策略 800 局。两种策略都不使用道具，匹配后等待烹饪、送达和补单完成：

- 随机策略：在当前可取的牌中等概率选择。
- 贪心策略：优先完成当前订单，再补已有部分材料的当前订单，减少重复备料，随机打破同分；打分不读取后续菜单或埋牌类型。

版本 2 在v16菜单交接引擎下复核的基线如下（2026-11-13，牌堆生成参数未改，generatorVersion仍为2）；修改算法后用新结果替换此表：

| 档位 | 材料种类均值 | 遮挡边数均值 | 见证峰值均值 | 贪心通关率 | 随机通关率 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 入门 | 4.98 | 41.00 | 3 | 100.00% | 53.63% |
| 家常 | 9.84 | 41.08 | 4 | 68.50% | 0.00% |
| 忙碌 | 11.96 | 60.00 | 6 | 37.00% | 0.00% |
| 挑战 | 13.56 | 60.00 | 7 | 27.25% | 0.00% |

常规回归要求：入门贪心通关率至少 95%；家常比入门低超过 15 个百分点、忙碌比家常低超过 10 个百分点、挑战比忙碌低超过 3 个百分点；入门随机通关率比家常高超过 25 个百分点。这些是当前固定样本的回归门槛，重新定义档位目标时需同步审查测试。

历史v2曾扩样默认第1–10,000关。v16引擎本次常规回归为默认100关、四档400个种子、192条策略与引擎一致性，以及四档0.01秒快点完整回放；本次未重跑10,000关扩样。浏览器已核对四档画面及三料菜实际点击、上菜和补单；真机触摸、性能与真人难度仍待校准。

**指标边界**：上述通关率只比较固定策略，不代表真人胜率，也不保证相邻关卡逐关变难。后三档随机通关率均为零，不能再用它区分后三档。耗时受运行设备影响，桌面结果不能代替真机性能验收。

## 5. 调参步骤与约束

1. **确定问题与保留基线**：是入门容易卡槽、某档跨度太大，还是后续订单杂料过多；保存修改前的同样本分析输出。
2. **选一个主要变量**：先调 `prepLimit` 或菜谱数量；改变三料结构再调 `tripleDishes`、`tripleRecipes`；空间问题调 `bury`。`mixing = 0` 同时改变选菜偏好和材料调度，不能当成只影响交错的开关。
3. **固定样本对比**：保持关卡号、种子、策略和样本量一致，先跑默认分析，再用 `200 32` 扩样；检查档位之间的分布和异常种子，不只看总体平均。
4. **构建与回归**：运行下列命令，材料总账、无道具见证和真实引擎一致性必须通过。策略门槛失败时先分析原因，不直接放宽测试来掩盖退化。
5. **真人复核并更新文档**：试玩各档，记录失败时的备菜、剩余遮挡、已完成订单和道具使用情况；确定新参数后，替换本文件的参数、结果、适用版本与边界说明。

```sh
npm run build:wechat
npm test
npm run analyze:levels
npm run analyze:levels -- 200 32
npm run serve
```

例如家常档过难，可先仅把家常的 `prepLimit` 从 4 调到 3，保留其他参数与样本，比较贪心通关率、见证平均占用和真人卡槽情况。若未变易，应分析菜谱与遮挡交互，而不是预设参数变化必然有效。

调参必须满足：

- `tripleDishes` 为非负偶数；推导的双料份数必须为非负整数，材料总数保持 40。
- 当前流程同时使用双料和三料菜，需 `0 < tripleRecipes < recipeCount`；各类菜的份数不得少于该类菜谱种类数，保证每道菜至少一份。
- 构造预算建议 `3 <= prepLimit <= 7`；菜谱池必须能找到足够的兼容菜谱，不能靠提高搜索上限解决配方冲突。
- 不得移除真实引擎验证、在材料赋值后任意洗牌，或把玩家容量随档位一起改变。
- 修改层数、偏移或牌大小时，同步核对布局、渲染、点击和遮挡；修改飞行或烹饪时长时，同步检查生成回放的 `.3/10` 秒等待假设及策略一致性测试。

## 6. 代码入口、复盘与维护

| 内容 | 入口 |
| --- | --- |
| 档位、选菜、材料顺序、堆叠、回放与策略探测 | `shared/core/levels.js` |
| 有限补单、自动消费、容量和胜负状态 | `shared/core/game-core.js` |
| 配方与盘面尺寸 | `shared/data/recipes.json`、`shared/data/layout.json` |
| 难度验证与统计 | `tests/verify-levels.cjs`、`scripts/analyze-levels.cjs` |

复盘时使用同一版本、菜谱、布局、关卡号、档位和种子：

```js
const config = Levels.createLevel(recipes, layout, 12, {
  difficulty: 'hard',
  seed: 42
});
// 检查 dishPlan、orderPlan、ingredientCounts、solution、metrics。
```

浏览器右侧可直接切换前四关，也支持 `?level=1` 至 `?level=4`。重开同一关复现同一牌堆。`solution` 是开发验证数据，当前提示工具没有接入完整求解器，偏离见证后的提示不保证能救局。

修改生成规则导致同一种子牌堆变化时递增 `generatorVersion`，重新验证并更新基线；仅修改文档措辞无需改版本。统计脚本中的版本标记也须同步。文档保留当前方案、必要原因和适用边界，旧参数、旧结果及已放弃的设计用新内容替换，避免累积成变更日志。
