# 关卡配置、生成与难度验证

适用版本：`generatorVersion: 3`，2026-11-18。本文描述当前有效实现；调整配置或算法后替换参数与结果，不追加开发流水账。真人胜率、广告真机收益和生产性能仍需实测，不能用机器人分数替代。

## 1. 关卡数量与成长

首关是引导关：3 种双料菜、共 4 份成菜、8 张食材，先认识自动做菜、补单和上菜。后续增加总份数、菜谱种类和材料；总量封顶后，用几何与交错形成难度变化。

| 关卡 | 成菜份数 D | 菜谱种类 | 食材张数 N | 层数上限 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 4 | 3 | 8 | 1 |
| 2 | 5 | 3 | 11 | 2 |
| 3 | 6 | 3 | 14 | 2 |
| 4–6 | 7–9 | 4 | 17–22 | 2 |
| 7–10 | 10–12 | 4 | 25–30 | 3 |
| 11–20 | 13–16 | 5 | 33–42 | 3 |
| 21–40 | 17–20 | 6 | 45–54 | 4 |
| 41–60 | 21–24 | 6 | 57–66 | 5 |
| 61 以后 | 24 | 6 | 66–72 | 5 |

设三料菜份数为 T，则 `N = 2 × (D - T) + 3 × T = 2D + T`。允许全双料、混合与全三料，不再要求 T 为偶数。硬上限为 24 份菜、6 种配方、72 张牌、5 层；同时收料仍最多三桌，主备菜始终七格，暂存容量二。

前 60 关逐关配置。随后使用五个封顶菜单计划循环，第 61–100 关有筛选后的种子表；更后面的关卡复用同一菜单计划的精选种子库，避免默认发出未校准的全新牌堆。仅当相应种子库为空时，才回退到关号派生种子。循环计划是有限内容的扩展，不等同于无限独立手工关卡。章节整体增长，章内保留缓和关及挑战关；后期缓和关使用较浅的灯笼结构，而非继续增加牌数。

## 2. 直接调整某关的菜谱

唯一生产入口是 `shared/data/level-config.js`，三端读取同一份配置。`shared/data/recipes.json` 定义配方和单价；关卡配置不重复填写材料总数或收入。

```js
{
  level: 1,
  difficulty: 'easy',
  shape: 'pairs',
  layers: 1,
  seed: 7919, // 实际精选值以文件为准
  orders: [
    ['d01', 'd01'], // 桌一：番茄炒蛋两份，严格按此顺序补单
    ['d02'],        // 桌二：青椒肉片一份
    ['d04']         // 桌三：西兰花虾仁一份
  ]
}
```

- 每个数组是一桌的完整有限队列；每次出现一个 ID 就代表一份菜。重复 ID 表示重复份数，不是新增菜谱种类。
- 改某关只需改该行 `orders`。材料总账、成菜份数、单价合计和预期收入自动推导；补单不再随机改写队列。
- `levels` 从 1 开始连续编号，不能重复或留空；新增手工关追加在末尾。`repeat` 控制手工关之后的循环计划，`seeds` 控制扩展关的精选种子。
- `shape` 支持 `pairs / islands / ring / bridge / lantern / twins`；`layers` 必须能容纳实际材料，且不超过全局上限。不为多牌缩小现有牌尺寸。
- `difficulty` 选择下面的构造参数。它不是实测难度分数，必须重新分析。
- `seed` 为 0–4294967295 的整数；同版本、配置、布局和种子确定性复现。更新配置后内容指纹 `contentId` 改变，首通去重仍只依据主线关号。
- 可在某条配置中增加 `greedyTarget: [下限, 上限]`，覆盖候选筛选的默认无道具贪心目标。它不是真人胜率。
- `levels:generate --apply` 会重新格式化这份数据并写回种子，保留队列和支持的配置字段；先检查候选报告，再应用。

## 3. 构造参数、几何与约束

| 档位 | 构造备菜峰值预算 | mixing |
| --- | ---: | ---: |
| easy 入门 | 3 | 0 |
| normal 家常 | 4 | 1 |
| hard 忙碌 | 6 | 2 |
| expert 挑战 | 7 | 3 |

`prepLimit` 只约束构造见证，玩家始终七格；见证峰值不是最优路线的最低容量。mixing=0 偏向即时成菜，其他值偏向交错与持料，不是难度倍率。

`shared/data/board-templates.js` 定义六种轮廓。0 格始终留空，牌位按轮廓从中心向外生长；按总牌数从下到上分配准确数量，上层位置由下层支撑。相邻层交替使用 `(32,-24)` 偏移，最终整体居中于 `(55,536,818,791)` 的食材区。保持原牌大小与触摸尺寸，层数增加不压缩字体或食材。

`board-geometry.js` 统一矩形相交、遮挡图和绘制顺序。所有更高且相交的牌都算遮挡者；全部移走后才可选。绘制和引擎按同一层级顺序排列，输入反向命中；任意层解锁都能反馈，不再只处理 layer=0。

配置与生成必须满足：

- 每种配方各材料一份，完整材料与所有订单逐项相等。
- 整个菜谱池不得互为配方子集；任意可能同屏的三桌不能共享同一种食材。
- N≥20 时，全关单料最多 `ceil(N×0.20)` 张。
- 开局单料最多 `ceil(可取牌数×0.30)` 张；小盘面取整后实际比例可能高于 30%，报告同时给数量和分母。此约束不套用到残局。
- 同层不能重叠，全部牌在实际绘制区内，形状有足够牌位。
- 摆牌在 24 个合法拓扑分配候选中降低开局集中与同料相邻；不允许在生成见证后任意洗牌。

## 4. 生成与可解保证

```text
配置三桌完整队列 → 菜品/材料总账 → 对应数量的形状牌位
→ 受备菜预算限制的材料序列 → 合法拓扑顺序赋值
→ 开局集中与相邻材料筛选 → 真实 Engine 回放至最后送达
```

材料序列搜索维护库存、备菜与订单游标，缓存失败状态，最多 20,000 个节点。几何不决定材料预算。每个返回的牌堆都必须有一条真实引擎验证的无道具见证，否则抛出明确错误，不返回未验证牌堆。

稳定模型每次等待材料和菜单交接完成；真实回放另外覆盖连续输入、容量预约、烹饪与送达。生产生成只运行有界构造，完整候选搜索及分析留在开发工具中。

## 5. 求解、提示与救援

`level-search.js` 用 BigInt 表示 72 张牌，保留备菜的顺序、来源、暂存位置、订单游标与剩余工具，不能把两格暂存等价为主槽九格。

搜索返回三态：`solved / unsolvable / unknown`。只有穷尽该预算的状态空间才能证明无解；超出节点预算记 unknown。所有找到的路线还需真实引擎回放确认。最低容量给出上下界，安全选择比例给出已证明范围，不把未知当成失败。

生产提示从当前实际状态求解，在副本上完成在途、换单和厨房，再验证后续路线。预算默认 4,000 个节点；未知、无解或第一步不是当前可选牌时不扣次数。它使用完整信息，是道具能力，不是普通玩家机器人。

激励救援保留主槽七格、暂存二格，每局最多两次额外救援。只提供已验证存在后续路线的撤回/暂存；优先选择不需要后续视频的操作。部分局面需要两次救援才有解，部分状态不可救或预算内未知，不承诺看完必过。

`App` 注入 `rewardedRescue`，无真实广告配置或尚未加载成功时不展示失败救援入口。两端配置为各自 `src/ad-config.js`；只有 SDK `onClose({isEnded:true})` 完成回调才能发放。show/load 成功不是奖励。广告期间暂停并重置帧时间；取消、错误、重复回调、重开、换关与释放会话不发入新局。Web 实验室的离线记录回放与生产广告分离。

## 6. 自动工具与复现

已有命令均从仓库根目录运行：

```sh
npm run build
npm test
npm run test:levels
npm run test:levels:full
npm run test:levels:ui
npm run analyze:levels -- --levels 1:100 --trials 32 --cases
npm run analyze:levels -- --levels 1,20,40,64 --trials 16 --policies greedy,lookahead --tools --solve
npm run levels:generate -- --levels 1:100 --candidates 100 --trials 64 --seed 20261118
npm run levels:generate -- --levels 1:100 --candidates 100 --trials 64 --apply
npm run levels:replay -- --level 20 --policy greedy --policy-seed 997 --budget free
npm run levels:replay -- --case reports/levels/replay.json
npm run serve
```

- 分析支持 `--levels 1:20` 和 `--levels 1,20,40:45`。旧位置参数 `200 32` 现在表示实际第 1–200 关、每副每策略 32 次，不再强制覆盖四档同一个 40 张牌结构。
- 分析输出 JSON 与 CSV，逐关给菜谱、张数、层数、开局材料、策略分数与未知救援数；`--cases` 保存代表失败路径。`--solve` 增加 oracle、最低容量上下界和根状态安全选择范围；大型关卡宜按需单独运行。
- `--tools` 比较 none（零道具）、free（1/2/1）、ad1、ad2；随机策略始终单独测零道具。实际工具行为和暂存取回均通过引擎执行。
- 策略为 random、greedy、unlock、lookahead。greedy 只看当前订单和可取牌；unlock 还使用遮挡几何，不是普通玩家胜率预测；lookahead 只前瞻当前已知订单和可取材料，不读取隐藏食材和后续菜单。oracle 明确读取完整信息。
- 候选先用 16 次贪心初筛，保留最多 12 个和原配置种子，再按指定 trials 复核。超出目标时默认拒绝写回；`--allow-outside` 仅供显式开发试验，不应当作正常验收。
- 失败记录含生成器版本、配置、种子、配方/布局 SHA-256、策略版本、策略种子、道具预算、动作与结果。CLI 校验版本与哈希，不兼容时要求对应源码。可重放稳定操作，也可重放实验室导出的 tick/pause 时间轴。
- `reports/levels/` 为忽略的开发产物，测试脚本和候选库不进入 native 包。

浏览器实验室：`http://127.0.0.1:4173/platforms/web/lab/`。支持逐关配置 JSON 预览、真实取牌、任意层剖面、当前状态求解、单步和整条见证、三种基础策略、记录导入导出。它不读写经营存档，剖面不改变真实可选关系，离线局时不作为真人局长。复杂工具预算与批量比较走 CLI。

工具对照每副 16 次的例子：第 20 关零道具/免费/一次额外/两次额外救援为 43.75%/68.75%/68.75%/87.50%；第 64 关为 25%/31.25%/50%/62.50%；第 60 关为 18.75%/25%/31.25%/37.50%。不能把少量机器人结果当作广告转化或真人达标，尤其后期仍需校准。

常规策略回归要求：第 1–3 关至少 98%，第 4–10 关至少 75%；随后三个阶段均值分别下降超过 8、10、5 个百分点。调整目标时先分析问题，不放宽测试掩盖退化。

真人首轮每档约 20–30 人找问题，量化验收再收集足够独立首尝试样本并给置信区间；重试与首次分开。广告收益先用随机分配的免费救援预算对照，不能直接比较主动看广告的人与不看的人。

## 8. 调整与发布流程

1. 修改单关 orders、形状、层数或构造档位；先检查材料总账及配方兼容。
2. 固定样本分析，检查逐关分布和异常种子；对候选结果做独立策略种子复核，避免只调到机器人样本。
3. 生成候选，检查 JSON，再显式 `--apply` 写回种子；实验室复核教学、关键节点及残局。
4. 执行完整 build、npm test；算法改动追加 `test:levels:full`。真实手机检查触摸、识别、帧率、后台、字体与广告。
5. 重算首通收入、收藏和装扮节奏；首通关号去重及历史钱包不变。更新本文和经营文档。

算法改变导致相同输入发牌变化时递增 generatorVersion；只改具体队列或种子由内容指纹区分。当前无账户/云存档、真人校准与正式广告单元验收，不把本地模拟通过写成发布验收完成。
